# Full app reset boundary — 18 November 2026

Scope: [#44](https://github.com/matchalattewithbanana/Tempo/issues/44), based on main `4d849e7`. This is source work for a future build; published `4.9.0-beta.1` APKs retain the older partial-clear implementation.

## Decision and scope

Clear all data now delegates to `ActivityManager.clearApplicationUserData()`. Android owns process termination and app-data removal, rather than Tempo deleting Room tables and a single DataStore while other writers keep running. There is no partial-clear fallback and no manual service-stop/final-flush sequence that could persist an old session after table deletion.

The local reset covers app-private database/preferences, account and pairing stores, offline/quarantined events, session recovery, appearance/profile data, local reporting queues, WorkManager state, caches and app-specific external storage. Android also clears notifications, runtime permissions and URI grants. The installed app remains. Files outside app-specific storage, cloud backups, provider accounts, companion stores and already-delivered telemetry remain external to this reset.

The app closes and requires setup on explicit reopening. A successful API return means the request was accepted; Tempo does not announce verified deletion completion. Rejected/exceptional requests show a localized error and can be retried. Confirmation is scrollable, explains closure/scope in six languages and disables repeat/cancel actions while the request is pending. The old immediate navigation-to-onboarding callback has been removed throughout the call chain.

## Platform evidence

- [Android API contract](https://developer.android.com/reference/android/app/ActivityManager#clearApplicationUserData()): available since API 19 (Tempo supports API 26+), equivalent to clearing the app’s data in Android settings; defines storage/permissions/URI/notification scope and acceptance semantics.
- [Android 15 ActivityManagerService source](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android15-release/services/core/java/com/android/server/am/ActivityManagerService.java): `clearApplicationUserData` force-stops the package before invoking package-data removal; cancels scheduled jobs and alarms, revokes URI access and resets notification state.

This uses the platform’s package/process boundary rather than assuming cancellation of a few named workers covers every coroutine, HTTP callback, service queue and restore operation. It is a local reset, not remote account revocation or a forensic erasure certification.

## Opt-in destructive emulator probe — not executed

`AppResetBoundaryProbe` is skipped by normal instrumentation runs. Both methods require `allowDestructiveResetProbe=yes` and emulator hardware `ranchu` or `goldfish`. Use only a disposable emulator and separately authorized, installed debug/application-test APKs. It intentionally deletes that installation’s data and kills its own instrumentation runner.

1. `requestResetWithPendingData` seeds a real Room track/play, offline and quarantined queue data, a persisted active session, Spotify credentials/PKCE state, an onboarding flag, app/cache files and delayed tagged WorkManager work. It starts an independent delayed file writer, then calls the same production reset wrapper. The runner should disappear before its normal completion.
2. In a separate invocation, `verifyAfterReset` restarts instrumentation and verifies the old history, recovery/session/credential/PKCE/onboarding state, private files, delayed-writer output and tagged work are absent. It waits beyond the old writer’s deadline. A failed first invocation alone is never a passing result.

Example commands, **only for a disposable emulator** already prepared as above:

```bash
adb -s emulator-5554 shell am instrument -w \
  -e class 'me.avinas.tempo.data.reset.AppResetBoundaryProbe#requestResetWithPendingData' \
  -e allowDestructiveResetProbe yes \
  me.avinas.tempo.test/androidx.test.runner.AndroidJUnitRunner

# Inspect the runner termination and confirm the target process stopped before verification.
adb -s emulator-5554 shell pidof me.avinas.tempo

adb -s emulator-5554 shell am instrument -w \
  -e class 'me.avinas.tempo.data.reset.AppResetBoundaryProbe#verifyAfterReset' \
  -e allowDestructiveResetProbe yes \
  me.avinas.tempo.test/androidx.test.runner.AndroidJUnitRunner
```

Run the two selected methods independently. Do not invoke the whole probe class with the destructive flag. The verification invocation explicitly starts the package again; the preceding process check must occur first.
